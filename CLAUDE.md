# AI Detective — Backend

Node.js API for a story-driven web app that teaches learners to build an AI
agent by writing small pieces of code inside a detective narrative.

Reference documents live in `docs/`:

- `docs/architecture.md` — system design, data model, endpoint list
- `docs/project-scope.md` — what is in and out of scope

Read the relevant one before changing anything structural.

---

## Stack

| Layer | Technology |
|---|---|
| Runtime | Node.js 24+, Express 5, TypeScript |
| Database | PostgreSQL 18 via Prisma |
| Auth | Better Auth — email OTP plugin, bearer plugin |
| Email | Brevo |
| AI | LLM provider with streaming replies |
| Hosting | Single Google Cloud VM, Mumbai, behind nginx |

The frontend is a separate repository (React, Vite, TypeScript). Both are
served from one domain in production: the site at `/`, this API at `/api`.

---

Use the version in `.nvmrc` locally — `nvm use` in the repo root — so every
machine runs the same one.

## How work is organised

Tasks live in `tasks/NNN.md`, numbered from 201. Each has a goal, in scope,
out of scope, acceptance criteria and constraints.

When asked to implement a task:

1. Read the task file first.
2. Confirm the acceptance criteria back before writing code.
3. Stay inside the task. Do not build ahead into later tasks, even when the
   next step is obvious.
4. Finish by adding the new endpoints to `requests.http`.

## Non-negotiables

These are design decisions, not preferences. Do not change them without being
asked explicitly.

**No code execution, ever.** Learner code is text. It is stored, compared and
exported. It is never run, evaluated, or passed to anything that runs it.
There is no sandbox and no Python runtime anywhere in this system.

**Bearer tokens, no cookies.** Sessions are bearer tokens issued by Better
Auth and held in the browser's localStorage. Do not add cookie-based sessions.

**Better Auth owns its tables.** The `user`, `session`, `account` and
`verification` models are generated by its CLI. Do not hand-edit them. The
user id is a string, not an integer — every app model references it as text.

**Content is data.** Courses, chapters, story screens and quizzes come from a
content bundle produced by the frontend build. Course and step references are
permanent string IDs. Never store or derive progress from array positions or
chapter numbers.

**Timestamps are UTC.** Stored as `timestamptz`, always UTC. The only place a
local timezone appears is the Google Sheet export, which converts to IST
because the client reads it directly.

**`GET /me` is the only way the client reads the learner.** It returns the
learner and their profile together, in one call, on application load. Never
add a second endpoint for the profile — the frontend caches this response and
does not refetch it.

## Conventions

**Routes are thin.** A route handler validates, calls a service function, and
returns. Business logic and database access live in `src/services/` and
`src/db/`, one file per area. No Prisma queries inside route handlers.

**Validate every input with Zod.** Body, params and query. Use the shared
validation middleware rather than validating inline.

**Every protected endpoint resolves a learner id first**, through the session
middleware, and returns only that learner's own data. There is no endpoint
that returns another learner's anything.

**One error shape.** Every error response is:

```json
{ "status": 400, "code": "INVALID_INPUT", "message": "...", "requestId": "..." }
```

Thrown errors go through the central handler. Do not construct error responses
inline in route handlers.

**Row ids are `bigint` auto-increment.** No row id is ever exposed in a URL
or returned to the browser, so there is nothing to guess and short numbers are
far easier to work with when inspecting the database or the attempt log. The
learner id is the exception: it is text, because Better Auth generates it.

**`soundOn` means the sound plays.** The field, the `sound_on` column and the
interface all use the same polarity. Never introduce a mute-phrased name
anywhere — an inverted meaning between layers is a bug waiting to happen.

**Every error is logged exactly once, in the central error handler**, with
its request id and full stack. The rules that follow from that:

- Route handlers have no try/catch. Express 5 forwards rejected promises from
  async handlers to the error handler automatically.
- Services throw. They do not catch and log.
- Catch only where you can do something about it — add context the caller
  lacks, apply a fallback, retry, or translate a third-party error into an
  application error. Then rethrow. Never catch purely to log.
- Fire-and-forget work is the exception and must catch. The Google Sheets
  sync and the feedback email run after the response has gone, so no handler
  is listening. An uncaught rejection there can take the process down. Each
  needs an explicit catch that logs and moves on.
- Process-level handlers for `uncaughtException` and `unhandledRejection` log
  and then exit, so nothing escapes even when the design fails.

Nothing ever fails silently, and no failure appears five times from five
layers.

**Structured logs.** JSON lines with a request id, written to file with
rotation. The request id in a log line matches the one in the error response,
so a reported bug can be traced.

## Security rules

**Never log secrets.** OTP codes, bearer tokens, session ids, API keys and
learner email addresses do not go into the log file. The dev-mode OTP console
output is the single exception and is guarded by the environment check.

**Email sending is off by default.** The Brevo wrapper is driven by
`EMAIL_MODE`, which is `console` unless explicitly set to `live`. An
unrecognised or missing value means `console`. No test, seed script or
fixture may set it to `live` — the daily send limit is shared with production.

**Secrets live in `.env` only.** `.env` is gitignored. `.env.example` lists
the variable names with no values. Never commit a key, never put one in a
comment, never echo one in a log line.

**Rate limit anything that costs money or sends email.** Sign-in, Saral and
feedback endpoints all have limits. Saral's limit is the AI cost ceiling.

**Trust nothing from the client.** `attempt_number` is computed server-side
from existing rows. Learner ids come from the session, never from a request
body or query parameter.

## Mentor Saral

Saral is the in-app AI mentor. His knowledge is the course content bundle,
injected whole into a cached system prompt.

- The whole course goes in the cached block, identical for every learner —
  per-learner trimming would break prompt caching.
- He must not discuss content from chapters ahead of the learner's position.
- He is available on chapter and story screens, never during quizzes. The
  endpoint refuses requests that originate from a quiz step.
- Hints come from the chapter instructions and task. The `saralNotes` field
  contains the solution and is only used when the learner explicitly asks for
  the answer.
- Every exchange is logged to `saral_messages` with its token counts.

## Out of scope

Do not build these, and do not suggest them mid-task:

- Code execution or sandboxing of any kind
- Password sign-in, password reset, social sign-in
- Server-side quiz scoring — quizzes are scored in the browser
- Admin or content-authoring interfaces
- Automated test suites beyond the targeted tests named in task files
- Analytics implementation and deployment automation — these are a later
  milestone

## Testing

`requests.http` at the repo root holds one request per endpoint in journey
order, with variables for base URL and token. Every new endpoint adds its
request there in the same task that builds it.

`npm run seed` creates two test learners with known progress so the collection
is repeatable.

Targeted tests exist only where manual checking cannot reach: OTP expiry,
single use and attempt locking; and ownership — that learner A cannot read or
change learner B's data. Test setup forces `EMAIL_MODE=console`.
